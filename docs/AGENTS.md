
# AGENTS.md — 기본 프로젝트 AI 개발 가이드

> 이 파일은 프로젝트의 **AI 개발 규칙에 대한 단일 원본(SSOT)**입니다. AI 코딩 도구는 작업 전에 이 파일을 확인하며, 도구별 지침 파일(`CLAUDE.md` 등)은 이 문서를 참조하도록 설정합니다. (도구마다 자동 로딩 방식이 다르므로 자동 참조 여부를 확인합니다.)
>
> 이 문서는 **스택과 관계없는 공통 규칙**입니다. 스택별 문법·폴더·명령어·예시 코드는 `docs/requirements.md` 0장에 지정한 **스택 파일**에 있습니다. 두 문서는 함께 적용하며, 스택 파일은 공통 규칙을 그 스택으로 구현하는 방법만 정의합니다.

---

## 1. 프로젝트 개요

- **이 문서는 프로젝트마다 수정하지 않습니다.** 프로젝트 이름·설명·대상 사용자·**스택**은 `docs/requirements.md` 0장에서만 정의합니다.
- **작업 범위:** **퍼블리싱 전용**
- **스택 파일:** `docs/requirements.md` 0장에 지정된 스택 파일(`docs/stack/react.md`, `vue.md` 중 하나) **하나만** 읽습니다. 다른 스택 파일은 읽지 않습니다. 스택이 지정되어 있지 않으면 작업을 시작하지 않고 사용자에게 확인합니다.
- **문서 읽기 순서:** `AGENTS.md` → `docs/requirements.md` 0장(스택 확인) → 스택 파일 → `docs/requirements.md` → `docs/design.md` → `docs/tasks.md`
- **디자인 원본:** 사용하는 디자인 툴과 링크·파일 위치는 `docs/requirements.md` 6장에서만 정의합니다. 이 문서의 "디자인 원본"은 그곳에 지정된 시안을 뜻합니다.
- **작업별 추가 문서:** IA 작업은 `docs/ia-spec-{스택}.md`, Guide 작업은 `docs/guide-spec-{스택}.md` (React → `ia-spec-react.md`, `guide-spec-react.md` / Vue → `ia-spec-vue.md`, `guide-spec-vue.md`). 실제 파일명은 스택 파일 1장에 있습니다.
- 문서가 없거나 내용이 불명확하면 가정하지 않고 사용자에게 확인합니다.

## 2. 기술 스택 및 라이브러리

프레임워크·언어·빌드 도구는 스택 파일 1장을 따릅니다. 아래는 모든 스택에 공통입니다.

| 구분 | 사용 기술 | 규칙 |
| --- | --- | --- |
| 스타일 | 일반 CSS | `common.css`, `ia.css`, `guide.css`만 사용 (5.3절) |
| 슬라이드 | Swiper | 슬라이드·캐러셀 구현 시 필수 (5.6절) |
| 패키지 매니저 | npm | 기존 의존성 우선 |

**사용 금지**

- Tailwind CSS, SCSS, CSS Modules, styled-components, Emotion 등 다른 스타일 방식
- MUI, Ant Design, Vuetify 등 UI 컴포넌트 라이브러리
- Lucide, Font Awesome, React Icons 등 외부 아이콘 라이브러리
- 전역 상태 관리 라이브러리
- 스택별 금지 항목은 스택 파일 1장을 따릅니다.

**설치 정책**

- 기존에 설치된 라이브러리를 우선 사용합니다.
- **Swiper만 사전 승인**되어 있어 필요 시 `npm install swiper`로 설치할 수 있습니다.
- 그 외 신규 라이브러리는 이유와 영향 범위를 설명하고 승인받은 뒤 설치하며, 이 문서를 갱신합니다.

- 작업 완료 시 스택 파일의 빌드 명령으로 확인하고, 실행하지 못했다면 그 사실을 명시합니다.

## 4. 프로젝트 폴더 구조

- 기준 폴더 구조는 **스택 파일 3장**을 따릅니다.
- 기준 구조에 있는 폴더는 필요할 때 생성합니다.
- 구조에 없는 폴더는 `docs/requirements.md`에 정의되어 있거나 사용자가 승인한 경우에만 추가하고 스택 파일을 갱신합니다.
- 공통 컴포넌트는 공통 컴포넌트 폴더, 페이지는 페이지 폴더에만 만들며, **컴포넌트·페이지마다 폴더를 만들지 않고 파일 하나로 둡니다.**
- `/Ia`, `/Guide`는 공통 레이아웃 밖 독립 화면으로 두고 각 화면에서 전용 CSS를 불러옵니다.

## 5. 코딩 규칙

### 5.1 컴포넌트

- 컴포넌트 작성 문법(선언 방식, 내보내기, Props 정의)은 스택 파일 4장을 따릅니다.
- 이벤트 핸들러(컴포넌트 내부 함수)는 `handle` 접두어를 사용합니다.
- 약 150줄을 넘으면 분리를 검토하되, 줄 수만을 이유로 쪼개지 않습니다.

**공통 컴포넌트 기준**

- 같거나 비슷한 UI가 **2곳 이상**에서 쓰이고 구조·동작을 공통화할 수 있을 때만 공통 컴포넌트로 분리합니다.
- 1곳에서만 쓰는 UI는 해당 페이지 파일 안에 작성합니다.
- "나중에 쓸 수도 있다"는 이유로 미리 만들지 않습니다. 단, 6.4절 2단계(화면 분석)에서 2곳 이상 사용이 확인된 컴포넌트는 페이지보다 먼저 만듭니다.
- 기존 공통 컴포넌트가 있으면 새로 만들지 않고 재사용하며, 데이터와 상태는 Props로 제어합니다.

### 5.1.1 공통 컴포넌트 설계 규칙

아래는 개념 규칙입니다. 각 개념을 스택에서 어떻게 구현하는지는 **스택 파일 5장 대응표**를 따릅니다.

**Props 규칙**

| 구분 | 규칙 | 예시 |
| --- | --- | --- |
| 이벤트 | `on` + 동사 (컴포넌트 내부 함수는 `handle`) | `onClick`, `onChange`, `onClose` |
| Boolean | HTML 속성과 같으면 그대로, 아니면 `is`/`has` | `disabled`, `isOpen` |
| 변형 | 정해진 문자열 값 중 하나 + 기본값 | `variant`: `'primary'` \| `'secondary'` |
| 크기 | 정해진 문자열 값 중 하나 + 기본값 | `size`: `'sm'` \| `'md'` \| `'lg'` |
| 내용 | 텍스트만이면 `label`, 마크업이 들어가면 자식 콘텐츠 | |

- variant·size 값은 **디자인 원본에 있는 것만** 정의합니다.
- 공통 컴포넌트는 외부에서 **클래스를 받아 모양을 바꾸지 않습니다**. 배치·간격은 부모 요소에서 처리하고, 새 모양이 필요하면 variant를 추가하고 Guide를 갱신합니다.

**폼 컴포넌트 (Input, Select, Checkbox, Radio 등)**

- 값은 부모가 가지고, 컴포넌트는 값과 변경 이벤트로 제어합니다.
- 변경 이벤트는 이벤트 객체가 아니라 **값만** 전달합니다.
- `label`과 입력 요소는 자동 생성한 고유 ID로 연결합니다. ID를 하드코딩하지 않습니다.
- 오류 상태는 `aria-invalid`, 오류 문구는 `aria-describedby`로 연결합니다.

**상태 클래스**

- 상태 클래스는 `on`(활성·선택·열림), `disabled`만 사용합니다. 예: `.tabItem.on`, `.accordion.on`
- 변형 클래스는 루트 클래스에 함께 붙입니다. 예: `.btn.primary`, `.btn.sm`

**오버레이 (Modal, Toast, Tooltip, 드롭다운 등)**

- Modal(및 Toast처럼 화면 전체 위에 뜨는 레이어)은 `#wrap` 안의 `<div id="modalWrap">`(Footer 다음)에 렌더링합니다. `body`에 직접 렌더링하면 `#wrap` 범위의 CSS가 적용되지 않으므로 금지합니다.
- Tooltip·드롭다운은 기준 요소 옆에 렌더링합니다. 부모의 `overflow: hidden` 등으로 잘리는 경우에만 `#modalWrap`을 사용합니다.
- 배경 스크롤 잠금은 열릴 때 `document.body.style.overflow = 'hidden'`, 닫힐 때 이전 값으로 복원합니다. 이는 이 절에 명세된 예외이므로 5.3.1 기록 대상이 아니며, CSS에 `body` 선택자는 여전히 쓰지 않습니다.
- Modal: `role="dialog"`, `aria-modal="true"`, `aria-labelledby`, ESC로 닫기, 열면 내부로 포커스 이동, 닫으면 연 버튼으로 포커스 복귀.

**반복 UI (Tabs, Accordion, Table 등)**

- 항목은 배열로 받습니다. 예: `items`
- 활성 상태는 기본적으로 컴포넌트 내부에서 관리하고, 외부 제어가 필요할 때만 `activeIndex` + `onChange`를 추가합니다.
- 키보드 조작과 ARIA 역할은 WAI-ARIA Authoring Practices 패턴을 따릅니다.

### 5.2 이름 규칙

| 대상 | 규칙 | 예시 |
| --- | --- | --- |
| 컴포넌트, 타입 | PascalCase | `UserCard`, `UserProfile` |
| 함수, 변수 | camelCase | `formatDate`, `isOpen` |
| 공용 상수 | UPPER_SNAKE_CASE | `MAX_ITEMS` |
| CSS 클래스, ID | camelCase | `.cardTitle`, `#mainContent` |
| Boolean 변수 | `is`, `has`, `can` 권장 | `isLoading`, `hasError` |

- 스택 고유 대상(예: React 커스텀 훅)의 이름 규칙은 스택 파일을 따릅니다.

### 5.3 CSS

- CSS 파일은 **`common.css`(일반 페이지), `ia.css`(`/Ia`), `guide.css`(`/Guide`) 세 개만** 사용합니다(위치는 스택 파일 3장). `*.module.css`, `Home.css`, `variables.css` 등 다른 CSS 파일을 만들지 않습니다.
- CSS는 한 번 불러오면 다른 화면에도 남을 수 있으므로 선택자 범위를 한정합니다.
    - `common.css`: `#wrap` 아래 (공통 레이아웃의 최상위 `<div id="wrap">`)
    - `ia.css`: `#iaWrap` 아래
    - `guide.css`: Guide 전용 클래스(`.guideWrap`, `.guide*`)만 사용
- `body`, `html`, `*`, `:root` 등 전역 선택자를 쓰지 않습니다. 리셋도 각 루트 아래에 작성합니다.
- 색상·간격·폰트 크기 등 반복 값은 `#wrap`에 CSS 변수(디자인 토큰)로 선언합니다. 토큰 목록은 `docs/design.md` 6장을 따릅니다.
- 반응형은 모바일 우선(`min-width`), 기본 브레이크포인트는 `768px`, `1024px`입니다.
- Swiper 등 승인된 라이브러리의 공식 CSS 불러오기는 허용하며, 스타일 재정의는 `common.css`에 작성합니다.

```css
/* 01. Design tokens */
#wrap {
    --color-text: #222;
    --space-4: 16px;
    --space-6: 24px;
    --radius-md: 8px;
}
/* 02. Reset / Base */
/* 03. Common components */
#wrap .card {
    padding: var(--space-4);
    color: var(--color-text);
    border-radius: var(--radius-md);
}
/* 04. Layout */
/* 05. Pages */
/* 06. Swiper custom styles */
/* 07. Responsive */
@media (min-width: 768px) {
    #wrap .card { padding: var(--space-6); }
}
```

### 5.3.1 인라인 스타일 예외 및 기록 규칙

- 인라인 스타일(`style` 속성)은 원칙적으로 금지합니다. **런타임에 계산되어 클래스로 미리 정의할 수 없는 동적 값**(진행률 `width`, 드래그·스크롤 위치, 데이터에서 받은 색상·이미지 URL 등)에만 허용합니다.
- 열림/닫힘처럼 정해진 상태는 클래스 토글로, 고정 값은 CSS로 처리합니다.
- 예외로 사용하면 **반드시 두 곳에 기록**합니다.
    1. **코드:** 요소 바로 위에 `[inline-style] 이유` 주석 (주석 형식은 스택 파일 5장)
    2. **문서:** `docs/design.md` 6.2절 표에 파일·요소·속성·이유·날짜 추가
- 인라인 스타일을 제거하면 주석과 표의 행도 함께 삭제합니다.
- IA 명세(`docs/ia-spec-{스택}.md`)의 IA 미리보기 `#wrap` 축소(`element.style`)는 명세에 포함된 예외이므로 기록하지 않습니다.

> 전체 사용 위치는 `grep -rn "\[inline-style\]"`로 찾아 design.md 표와 일치하는지 확인합니다.

### 5.4 이미지 및 아이콘

- 이미지·아이콘은 **디자인 원본의 에셋**을 `docs/requirements.md` 6장의 에셋 제공 방식대로 받아 사용합니다. 임의 제작, 유사 아이콘 대체, CSS로 모양 그리기, 디자인 원본에 없는 에셋 추가를 하지 않습니다. 원본을 구할 수 없으면 사용자에게 확인합니다.
- 아이콘은 `icons/`(가능하면 SVG), 이미지는 `images/` 폴더에 두고(위치는 스택 파일 3장), 파일명은 용도를 알 수 있게 작성합니다. 예: `iconSearch.svg`
- 같은 에셋을 중복 저장하지 않으며, 크기·배치는 CSS로 조정합니다.
- 정보 전달 이미지는 의미 있는 `alt`, 장식용은 `alt=""`를 사용하고, 아이콘 버튼·링크에는 접근 가능한 이름(`aria-label` 등)을 제공합니다.

```html
<button type="button" aria-label="검색">
    <img src="iconSearch.svg" alt="" />
</button>
```

### 5.5 상태 관리 원칙

- 같은 상태를 중복 관리하지 않고, 계산 가능한 값은 원본 상태에서 도출합니다.
- 상태는 그 상태를 쓰는 가장 가까운 공통 부모에서 관리합니다.
- 상태를 바꿀 때 배열·객체의 불변성을 유지합니다.
- 상태 관리 문법과 타입 규칙은 스택 파일 6장을 따릅니다.

### 5.6 슬라이드(Swiper)

- 슬라이드·캐러셀은 **Swiper**로 구현하며, 이동·터치·드래그를 직접 구현하지 않습니다. 슬라이드가 아닌 콘텐츠에는 쓰지 않습니다.
- 설치된 Swiper 버전의 공식 API를 쓰고, 반응형은 `breakpoints`, 자동 재생·페이지네이션·네비게이션은 Swiper 모듈을 사용합니다. 이들은 디자인·요구사항에 있을 때만 추가합니다.
- 여러 화면에서 쓰는 슬라이드는 공통 컴포넌트로 두고, 이미 있으면 재사용합니다.
- 슬라이드 데이터는 배열로 관리하고 반복 렌더링하며, 각 항목에 고유 키를 사용합니다.
- 자동 재생 시 정지 수단, 키보드 조작 등 접근성을 고려합니다.
- 스택별 사용 방법과 예시는 스택 파일 7장을 따릅니다.

## 6. 퍼블리싱 작업 규칙

### 6.1 기본 규칙

- 목업 데이터를 사용할 수 있으며, 여러 화면에서 공유하는 목업은 데이터 폴더(스택 파일 3장)에 둡니다.
- 기존 마크업 구조와 CSS 클래스명을 최대한 유지합니다.
- 시맨틱 태그를 우선 사용하며, 공통 레이아웃의 태그·ID 구조는 `docs/design.md`를 따릅니다.

### 6.2 IA 페이지 (`/Ia`)

- 상세 명세의 기준 원본은 **`docs/ia-spec-{스택}.md`**입니다. IA 관련 작업 전에는 반드시 전체를 읽습니다.
- 다른 작업에서도 지켜야 할 핵심 규칙:
    - IA 명세에 정한 IA 전용 파일만 사용합니다.
    - 기존 IA 디자인·문구·동작은 승인 없이 변경하지 않습니다.
    - 새 페이지를 만들면 **같은 작업에서** IA 화면 목록(`IA_TABLES`)에 등록합니다.
    - 검증되지 않은 페이지를 `Done`으로 표시하지 않으며, `docs/tasks.md`와 상태가 다르면 사용자에게 확인합니다.
    - `Guide` 항목은 항상 IA 목록 최상단에 둡니다.

### 6.3 공통 컴포넌트 Guide (`/Guide`)

- 상세 명세의 기준 원본은 **`docs/guide-spec-{스택}.md`**입니다. Guide 관련 작업 전에는 반드시 전체를 읽습니다.
- 다른 작업에서도 지켜야 할 핵심 규칙:
    - Guide 화면 파일 하나와 `guide.css`만 사용합니다.
    - 공통 컴포넌트를 추가하거나 Props·사용법을 바꾸면 **같은 작업에서** Guide를 갱신합니다.
    - IA는 페이지 목록, Guide는 공통 컴포넌트 설명입니다. 페이지를 Guide에 등록하지 않습니다.
    - Guide 변경이 없으면 결과 보고에 `Guide 변경 없음(공통 컴포넌트 변경 없음)`이라고 명시합니다.

### 6.4 작업 순서: 화면 분석 → 공통 컴포넌트·Guide → 페이지

디자인은 페이지 단위로 나오지만 작업은 공통 컴포넌트부터 합니다. 그래서 컴포넌트를 만들기 전에 **디자인 원본 전체를 분석해 공통 컴포넌트 목록을 먼저 확정**합니다.

**앞 단계가 완료(검증 및 `docs/tasks.md` 체크)되기 전에 다음 단계를 시작하지 않습니다.**

| 단계 | 작업 | 완료 조건 |
| --- | --- | --- |
| 1. 초기 구성 | 라우트, 공통 레이아웃(`#wrap`, `#modalWrap`), 디자인 토큰, `/Ia`, `/Guide` | 두 관리 화면 접속, IA에 Guide 등록, 빌드 통과 |
| 2. 화면 분석 | 디자인 원본의 **전체 페이지**를 보고 반복되는 UI를 찾아 컴포넌트 목록(이름, 사용 페이지, variant·size) 작성 | `docs/design.md` 2장 표에 기록, 사용자 승인, `docs/tasks.md`에 컴포넌트 작업 등록 |
| 3. 공통 컴포넌트 + Guide | 2단계에서 승인된 컴포넌트만 구현 | 컴포넌트마다 Guide 섹션(Props 표, 실제 UI, 사용 코드) 작성, 9.2 수동 검수 |
| 4. 페이지 | 공통 컴포넌트를 조합해 페이지 작성 | IA 등록, 디자인·동작 확인, 빌드 통과 |

- 2단계에서는 코드를 작성하지 않습니다. 사용 페이지가 2곳 이상인 UI만 공통 컴포넌트 후보로 올리고, 1곳뿐인 UI는 해당 페이지 파일 안에서 작성합니다.
- 컴포넌트 예시: `Input`, `Select`, `Radio`, `Checkbox`, `DatePicker`, `Button`, `Modal`, `Tabs`, `Accordion`, `Stepper`, `Table`, `Tooltip`. 실제 목록은 2단계 분석 결과 기준이며, 디자인 원본에 없는 컴포넌트나 Props·변형(variant)을 미리 만들지 않습니다.
- 시안이 페이지별로 순차 전달되면, 새 시안을 받을 때마다 2단계를 다시 수행해 목록을 갱신합니다.
- 4단계에서 공통 컴포넌트가 부족하면 페이지에서 복사하거나 CSS 덮어쓰기로 우회하지 않고, 컴포넌트를 수정하고 Guide를 함께 갱신합니다.
- 새 공통 컴포넌트가 필요해 보이면 페이지 작업을 멈추고 2단계로 돌아가 목록 추가를 제안합니다. 승인 후 컴포넌트와 Guide를 먼저 완료합니다.
- `docs/tasks.md`는 1 → 2 → 3 → 4단계 순으로 작성하고, 공통 컴포넌트 작업은 그것을 쓰는 페이지 작업보다 항상 위에 둡니다.
- 2단계에서 조회 목록 화면이 있으면 데이터 없음 영역의 디자인이 디자인 원본에 있는지도 함께 확인합니다. (6.5)

### 6.5 조회 목록 화면: 데이터 없음

**검색해서 결과가 0건이면, 목록 대신 "데이터 없음" 영역을 보여 줍니다.** 목록을 만들 때 이 영역도 반드시 같이 만듭니다.

- **위치:** 목록이 있던 자리에 목록 대신 보여 줍니다. 리스트·카드·슬라이드 등 형태와 관계없습니다.
    - 테이블만 예외: `<thead>`는 그대로 두고 `<tbody>` 안에 `<tr><td colspan="열 수">` 한 행으로 넣습니다.
- **동작:** 목업 데이터를 실제로 필터링해서, 결과가 없는 검색어로 조회하면 이 영역이 나와야 합니다.
- **함께 처리:** 총 건수는 0건으로 표시하고, 페이지네이션·더보기 버튼은 숨깁니다.
- **디자인:** 문구와 모양은 디자인 원본을 따르고, 없으면 임의로 만들지 않고 사용자에게 확인합니다.
- **공통화:** 2곳 이상에서 쓰이면 공통 컴포넌트(예: `EmptyState`)로 만들고 Guide에 등록합니다.
- 구현 예시는 스택 파일 8장을 따릅니다.

## 8. AI 작업 절차

1. **문서 확인:** 이 문서와 스택 파일, 관련 문서와 디자인 원본을 확인하고, `docs/tasks.md`에서 현재 작업과 6.4절 순서상 시작 가능한 단계인지 확인합니다.
2. **기존 코드 검색:** 새 파일을 만들기 전에 유사한 파일과 공통 컴포넌트가 있는지 찾습니다.
3. **작업 단위:** 요청된 작업 한 가지에만 집중합니다.
4. **최소 수정:** 요청 범위 밖의 리팩터링, 파일 이동·삭제·덮어쓰기, 라이브러리 설치는 사전 승인을 받습니다.
5. **불명확하면 질문:** 추측으로 설계를 확정하거나 디자인 원본에 없는 UI·기능·에셋을 추가하지 않습니다.
6. **IA·Guide 동기화:** 페이지 추가 시 IA, 공통 컴포넌트 추가·변경 시 Guide를 같은 작업에서 갱신합니다.
7. **검증:** 9.1절 자동 검사를 실행하고, 9.2절 수동 검수 항목 중 이번 변경에 해당하는 것을 정리합니다. 실행하지 않은 검사를 통과했다고 보고하지 않습니다.
8. **작업 기록:** 검증된 작업만 `docs/tasks.md`에서 `[x]`로 변경합니다. 수동 검수가 남은 작업은 사용자 확인 후 체크합니다.
9. **결과 보고:** 수정 파일, IA·Guide 반영 여부, 인라인 스타일 사용 여부(design.md 기록 여부), 변경 이유, 남은 문제를 요약하고, 마지막에 아래 **검수 결과** 표를 붙입니다. 명령어는 스택 파일 2장의 것을 적습니다.

```markdown
**검수 결과**

| 검사 | 결과 |
| --- | --- |
| 빌드 | 통과 / 실패 / 미실행(이유) |
| 린트 | 통과 / 실패 / 미실행(이유) |
| 규칙 검사 (check-project) | 통과 / 경고 N건(내용) / 미실행(이유) |
| 사람이 확인할 항목 (9.2) | 예: Modal ESC·포커스 복귀, 360px 레이아웃 |
```

- AI가 브라우저에서 직접 조작하지 못한 항목은 "확인함"으로 적지 않고 **사람이 확인할 항목**으로 넘깁니다.

### 8.1 Git 안전 규칙

- 작업 전 `git status`로 변경 범위를 확인하고, 사용자 변경분을 덮어쓰지 않습니다.
- `git reset --hard`, `git clean -fd`, 강제 푸시, 이력 재작성은 명시적 승인 없이는 금지합니다.

## 9. 검수

검수는 세 단계로 나눕니다. **기계로 확인할 수 있는 규칙은 9.1 자동 검사**로, **실제 동작은 `/Guide` 화면에서 9.2 수동 검수**로 확인하고, 마지막으로 **9.3 점검 목록**을 확인합니다.

### 9.1 자동 검사 (작업 완료 시 AI가 실행)

아래는 모든 스택에 공통인 검사입니다. 스택별 검사(린트 규칙 등)는 **스택 파일 9장**에 있습니다.

| 규칙 | 도구 | 확인 방법 |
| --- | --- | --- |
| 빌드 오류 없음 | 빌드 명령 | 스택 파일 2장의 빌드 통과 |
| `console.log` 없음 | 린트 또는 check-project | 디버깅용 출력 검색 |
| CSS 파일은 3개뿐 (5.3) | check-project | `.css` 파일이 `common.css`, `ia.css`, `guide.css`뿐인지 |
| 전역 선택자 없음 (5.3) | check-project | CSS에서 `body`, `html`, `:root`, 단독 `*` 선택자 검색 |
| `common.css` 선택자 범위 (5.3) | check-project | 모든 선택자(`@media` 내부 포함)가 `#wrap`으로 시작하는지 |
| 인라인 스타일 기록 일치 (5.3.1) | check-project | `[inline-style]` 주석 수 = `docs/design.md` 6.2 표 행 수 |
| 공통 컴포넌트 ↔ Guide 동기화 (6.3) | check-project | 공통 컴포넌트 파일마다 Guide에 섹션 `id` 존재 |
| 페이지 ↔ IA 동기화 (6.2) | check-project | 페이지 경로가 IA 데이터에 등록되어 있는지 |
| IA 최상단 Guide (6.2) | check-project | IA 목록 첫 항목이 `/Guide`인지 |

- `scripts/check-project.mjs`는 정적 보조 검사이며 실제 브라우저 동작 검증(9.2)을 대체하지 않습니다.
- 검사 항목을 추가·변경하면 이 표(또는 스택 파일 9장)와 `scripts/check-project.mjs`를 함께 갱신합니다.

### 9.2 컴포넌트 수동 검수 (사람이 `/Guide`에서 확인)

공통 컴포넌트를 추가·변경하면 `/Guide`의 해당 섹션에서 아래를 확인합니다. 해당 없는 항목은 건너뜁니다.

| 구분 | 확인 내용 |
| --- | --- |
| 모양 | 디자인 원본의 variant·size가 Guide에 모두 있고 디자인과 일치한다. |
| 상태 | `on`, `disabled` 상태가 Guide에 예제로 있고 올바르게 보인다. |
| 키보드 | Tab으로 이동되고 Enter·Space로 동작한다. 포커스 표시가 보인다. |
| 오버레이 | Modal은 ESC로 닫히고, 열면 내부로·닫으면 연 버튼으로 포커스가 이동하며, 배경 스크롤이 잠겼다가 복원된다. |
| 반복 UI | Tabs·Accordion 등은 WAI-ARIA 패턴대로 방향키·역할이 동작한다. |
| 폼 | 라벨 클릭 시 입력 요소에 포커스되고, 오류 문구가 `aria-describedby`로 연결된다. |
| 반응형 | 360px, 768px, 1024px에서 깨지지 않는다. |
| 문서 | Guide Props 표(Type·Default)가 실제 코드의 Props와 일치한다. |

- 수동 검수가 끝나기 전에는 해당 작업을 `docs/tasks.md`에서 `[x]`로 바꾸지 않습니다.
